# Конвейер компактной команды

## Принцип

Один вертикальный срез — один пользовательский сценарий от начала до результата. Сначала P0, потом P1. Параллелить можно только независимые этапы; общий код и состояние не редактируются одновременно.

## Оркестратор

Конвейером управляет единственный primary-агент `factory-lead`:

- модель `opencode-go/deepseek-v4.1-flash#max`;
- архитектор и диспетчер;
- запускает только `frontend-ui`, `logic-state`, `backend-db`, `qa-universal`;
- не пишет production-код, тесты и docs сам;
- проверяет `<thinking>`, handoff, файлы и gates;
- обновляет `factory/state/pipeline-state.json` только после приёмки;
- останавливается перед решением, которое требует человек.

## Стадии и зависимости

| Стадия | Агент | Вход | Выход | Зависит от |
|---|---|---|---|---|
| 00 Архитектура | `factory-lead` | `brief.md`, `PRODUCT.md`, `templates/`, код, `пример.jpg` | `architecture.md`, `contracts.md`, `decomposition.md`, `file-ownership.md` | — |
| 01 Фронтенд и UI | `frontend-ui` | 00 + текущий UI | UI-код, `ui-spec.md`, `handoff.md` | 00 |
| 02 Логика и стейт | `logic-state` | 00, 01, 03 | состояние, API-клиент, фильтры, `handoff.md` | 00, 01, 03 |
| 03 Бэкенд и БД | `backend-db` | 00 + текущий бэкенд | схемы, API, `api-changes.md`, `handoff.md` | 00 |
| 04 QA и docs | `qa-universal` | 01, 02, 03 | тесты, ревью, мелкие фиксы, README/docs, `handoff.md` | 01, 02, 03 |

## Что можно параллелить

- `frontend-ui` и `backend-db` — сразу после Gate 0, если контракты и file ownership зафиксированы.
- `logic-state` — после UI-контракта и API-контракта. Если контракты стабильны, можно стартовать раньше, но без редактирования файлов фронтенда и бэкенда.
- `qa-universal` — только после того, как код трёх программистов собран. Нельзя запускать QA параллельно с активными правками в тех же файлах.
- Нельзя параллелить двух агентов, которые пишут в одни и те же файлы.

## Quality gates

### Gate 0 — архитектура и декомпозиция

- [ ] Понятно, какой пользовательский сценарий считается главным.
- [ ] Известны границы: локальное демо, без реальных денег, auth — демо-слой.
- [ ] Определён приоритет P0/P1/P2.
- [ ] Есть `architecture.md`, `contracts.md`, `decomposition.md`, `file-ownership.md`.
- [ ] UI-контракт и API-контракт достаточны для параллельной работы.
- [ ] У каждой подзадачи есть владелец, вход, выход и критерий приёмки.

### Gate 1 — фронтенд и UI

- [ ] Экраны и состояния соответствуют UI-контракту.
- [ ] Нет горизонтального скролла на 375 px; touch-цели ≥ 44 px.
- [ ] Клавиатура, фокус, `Escape`, `aria-live`, `prefers-reduced-motion`.
- [ ] DOM-ориентиры и события переданы `logic-state`.
- [ ] `node --check` для изменённого JS проходит.

### Gate 2 — бэкенд и БД

- [ ] Схемы, индексы и API соответствуют контракту.
- [ ] Деньги — целые, операции идемпотентны, валидация на границе.
- [ ] Нет N+1 и необоснованных полных сканов.
- [ ] Ошибки понятны, секретов и стека в ответе нет.
- [ ] `node --check` и доступные тесты проходят.

### Gate 3 — логика и интеграция

- [ ] P0-сценарий проходит целиком.
- [ ] UI работает без API; при доступном API состояние согласовано.
- [ ] Инварианты инвентаря и баланса соблюдены.
- [ ] `localStorage` совместим с `so2cases.demo.v1`; повреждённые данные не ломают приложение.
- [ ] Демо-авторизация не собирает персональные данные.

### Gate 4 — QA и документация

- [ ] Unit-тесты детерминированы и запускаются одной командой.
- [ ] UI/E2E покрывает P0 и ключевую доступность.
- [ ] Результаты прогонов приложены, а не выдуманы.
- [ ] Баги по severity зафиксированы; мелкие исправлены, крупные возвращены владельцу.
- [ ] README и docs соответствуют коду и не обещают лишнего.

## Цикл QA

1. `qa-universal` принимает код трёх программистов.
2. Пишет unit/UI-тесты и проводит ревью.
3. Мелкие дефекты исправляет сам.
4. Крупные архитектурные проблемы возвращает владельцу файла через handoff.
5. Обновляет README/docs по факту кода.
6. Если тесты красные — Gate 4 не закрывается, `factory-lead` возвращает задачу.

## Шаблон постановки задачи агенту

```text
Роль: <agent-id>.
Цель: <один проверяемый результат>.
Входы: <файлы и артефакты>.
Выход: <файлы handoff>.
Границы: P0, локальное демо, не трогать <чужие файлы>.
Проверки: <команды или ручные шаги>.
Формат: начни с <thinking>, соблюдай factory/REASONING-PROTOCOL.md,
handoff — по factory/HANDOFF-SCHEMA.md.
```

## Остановка конвейера

Останови работу и верни задачу, если:

- агент не начал ответ с `<thinking>`;
- агент вышел за зону записи;
- результат противоречит `AGENTS.md`, `PRODUCT.md` или P0;
- проверки не выполнены, а в отчёте написано «работает»;
- появились реальные платежи, реальная auth, секреты или публичный деплой без разрешения;
- handoff не позволяет следующему агенту начать работу без догадок.

## Обновление состояния

`factory/state/pipeline-state.json` обновляет только `factory-lead`, а не субагенты. После каждого принятого handoff:

1. Поменяй `status` стадии на `done`.
2. Запиши `handoff` путь и `updatedAt`.
3. Добавь блокеры или решения в `notes`.
4. Не помечай стадию `done`, если gate не пройден.
